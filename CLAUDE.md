## What we're building

A MERN dating web app with a built-in AI agent. It is our entry for the **Nebius x NVIDIA Global AI Hackathon** (Devpost). The deadline is **Oct 30, 2026, 10:00 AM PDT (10:30 PM IST)**, and we target submitting on Oct 29.

**Problem:** dating apps match on preferences, not character. People find out after 2–3 conversations that a match isn't compatible.

**Solution:** after a match, the user's AI agent handles the early conversation for them. The agent:

1. checks the match's profile for fakes and inconsistencies
2. reads the match's profile and prompts to understand them before talking
3. holds the early conversation in the user's own voice, grounded in the user's personal knowledge graph
4. classifies the match as **Compatible / Maybe / Not compatible**, with evidence

Compatible means the user takes over the chat. Not compatible means the agent politely winds it down, and the user never spent time on it.

## Non-negotiable product rules

- **Consent at signup.** Every user must tick: "Early conversations with your matches may be handled by AI agents, including yours." Signup is blocked without it. Store `consentAgent: true` and `consentAt`.
- **Every message stores `authoredBy: 'human' | 'agent'`.** This is used for the audit log and the reveal at handoff ("your first 14 messages were handled by agents").
- **The user stays in control.** Agent modes are `off`, `shadow` (agent replies, user watches live, can take over) and `auto`. **Take over** is one tap and immediately stops the agent for that match.
- **The agent never invents facts about its user.** Anything it says about the user must come from the user's knowledge graph. If it needs something unknown, it deflects naturally and creates an "ask my human" question.
- **The agent respects disclosure tiers** (`public | if_asked | private`). Private facts are never sent to the model as sayable content.
- **No inference of caste, religion, ethnicity or race from names or photos.** Use religion only if the user lists it as their own stated preference or dealbreaker.
- **Keep demo and seed content SFW.** Judges review the video.
- **The other side of a conversation can be a human or another agent.** The code must work for both.

## LLM model routing

The exact model IDs come from `.env`. Copy them from `GET /v1/models` (run `server/scripts/smoke.js`) and never hard-code them.

| Env var | Model | Use for |
|---|---|---|
| `MODEL_FAST` | Nemotron 3 Nano | Conversation turns, quick classifiers |
| `MODEL_MID` | Nemotron 3 Super | Fact extraction, belief updates, trust check, seed generation |
| `MODEL_SMART` | Nemotron 3 Ultra | Final compatibility verdict ONLY (expensive) |
| `MODEL_EMBED` | Any embedding model on Token Factory | Fact embeddings |

**Gotcha:** the Nemotron models on Token Factory are reasoning models. If `max_tokens` is too small, the reasoning eats the budget and `content` comes back empty. Always set a generous `max_tokens` (≥ 2048 for chat turns), strip `<think>…</think>` and any reasoning field, and never let reasoning text reach a user-visible message.

All LLM calls go through `server/src/services/llm/client.js`. Nothing else imports `openai` directly.

## Knowledge graph — final design

- **`plan/15-knowledge-graph-final.md` is the source of truth** for everything the app knows about a user. It overrides plans 05–11 and `plan/kg-upgrade-reference.md` (which supplies implementation detail where plan 15 is silent). Plan 16 is the execution order.
- **Six layers:** (1) public `Profile`; (2) `Profile.gate` (basics, B answers, `accepts`, dealbreakers; gate code only); (3) self graph (`KgFact` with `observerId: null` + `KgEdge` + shared `Concept`); (4) voice (`VoiceProfile` + `VoiceSample`); (5) notes about others (`KgFact` with `observerId: me` + `ChatEvent`, quote-backed); (6) decisions (`MatchDecision`, mine only).
- **Information boundary:** another user's agent or judge may read my public `Profile` only in the trust check and the brief. It never reads my `KgFact`, `KgEdge`, `VoiceProfile` or `VoiceSample`. The only other cross-user paths are the transcript and the gate, which is code-only and returns a boolean. A DB-access spy test enforces this. `private` facts never reach a prompt whose output another user sees.
- **Conversation style is knowledge:** `VoiceProfile` stores distributions, not just means (word counts, emoji, laughs, endings, pet phrases, corrections, never-say) plus real `VoiceSample`s used as few-shot exemplars. The graph shows it as a correctable "How I text" hub.
- **Any language mix:** every sample is tagged with languages, script and whether it code-switches. `VoiceProfile.language` holds the mix, code-switch rate, switch triggers and `mirrorsLanguage`, and `planAct` picks each reply's language from it.
- **Matching stays swipe-based:** the gate filters the discover deck as one indexed Mongo query and re-checks (boolean) when a match is created. Discover order is random. Nothing ranks or compares two users' graphs or answers; overlap is discovered live, from the transcript against my own graph.
- **The engine is side-agnostic:** the other side may be an agent or a human typing (shadow mode); a human's messages are just transcript lines.
- **Per message:** at most 2 LLM calls (perceive+observe, generate), plus a stance check only when `mustDisagree`, plus at most 1 regeneration. Style and leak checks run in code. Seeded RNG per conversation.
- **Scaling rules:**
  - Embed concepts (shared, once for all users), not facts; only concept-less facts get their own vector.
  - Store vectors as compact BSON float32, loaded only when needed (`select: false`).
  - Caps: `MAX_SELF_FACTS` 150, `MAX_VOICE_SAMPLES` 200. TTL-archive closed matches' raw notes after `NOTES_RETENTION_DAYS`.
  - Async work runs through a Mongo `jobs` queue + worker (build, judge, compaction, voice rebuild, reflections, re-confirm, concept cleanup). No job scans all users.
  - Hot path: a per-conversation LRU cache of my facts + voice, keyed by `userId + graphVersion`.
  - Indexes from day one (plan 15 §6.6), including the gate query.
- **Thresholds:** all of them live in `services/kg/config.js`.
- **Checkpoint A decisions (plan 16):**
  - No migrations: wipe and re-seed. Dealbreakers fold into `isDealbreaker`. Deletes write a `KgTombstone`; trait PATCH/DELETE return 4xx.
  - The gate replaces `findClash`/`findOverlaps`/the agenda's "already known": `Profile.gate` + one indexed discover query + `$sample`, re-checked (boolean) at match creation. The brief stores nothing about the other user.
  - Both display names are stored on the match at creation. Date ideas use my own `shared_interest` events + my city. DB-spy whitelist for reading the other user's `Profile`: trust check, brief, and the human-UI routes in `matches.js`.
  - `ageMin`/`ageMax`/optional `radiusKm` on `Profile` and `Profile.gate`; city first, geo optional.
  - The Hinglish guard becomes the reply-language choice in `planAct`.
  - Stop rules become the interest meter + `planAct.end`; `MAX_TURNS` lives in `config.js`.
  - Judge job per side → `MatchDecision` with verbatim-quote validators. Shown as yes → Compatible, unsure → Maybe, no → Not compatible; the match is the lower of the two sides. Handoff only on mutual yes.
  - **Grounding costs no extra LLM call:** every self-claim cites fact ids, verified in code. A missing or contradicted citation triggers the single allowed regeneration. Plan 11 measures the unsupported self-claim rate offline (an LLM judge in eval scripts only). A code-side leak check (keyword/alias + embedding vs private facts) runs on every outgoing agent message.
  - Local dev and tests use `MongoMemoryReplSet` (`mongodb-memory-server` devDependency) so transactions work; never with `NODE_ENV=production`.
  - The plan-11B v1 work lives on branch `wip/plan-11b`; plan 11 v2 reuses `scripts/lib/runPair.js` and the `eval.js` report from it.
  - Every plan leaves the app runnable end to end (signup → onboarding → discover → match → agent chat), with the seed script updated to re-load data.

## Coding conventions

- Small modules, one responsibility each. Prompt text lives in `services/prompts/*.js` as exported template functions, never inline in business logic.
- Validate every LLM JSON output with zod, retry once on failure, then fail gracefully: log it and keep the app running.
- Every Express route uses async error handling and returns `{ error: { code, message } }` on failure.
- Every env var is validated at boot in `config/env.js`. Fail fast with a clear message.
- Never commit `.env`. Keep `.env.example` up to date whenever a new env var is added.
- Write a short `README` section or JSDoc only when it explains something non-obvious.
- Test as you go: each plan file ends with acceptance checks. Run them and report results before saying a task is done.
- Commit after each plan file with a message like `feat(plan-05): onboarding + knowledge graph`.
